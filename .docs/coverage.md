# 網羅性と保守リスク

調査日 2026年11月4日。context、ルート登録、画面、CLI、MCP、既存仕様を根拠に、実装の存在と担当範囲を整理した。運用上の網羅性は、通常操作に加えて、訂正・競合・再試行・復旧まで扱えるかで評価する。機能ごとの動作保証には受入テストと配備先の確認が必要になる。

## 現状の網羅性

- [System](layers/system.md)は、本人確認、操作権限、申請・承認、証跡、非同期連携の共通機構を広く備える。個別業務で誰が何を判断できるかは、利用側が定義する。
- [Company](layers/company.md)は、人・雇用・組織・責任・上長関係を扱う。人事台帳と組織上の資格を参照する基盤として使える。勤務実績や休暇残高の正本は業務側に必要になる。
- [業務context](layers/business.md)の専用機能は目標管理と評価、顧客台帳、商品・サービス台帳、クライアント案件と工数。勤怠、休暇、採用、購買などは、汎用申請で受付の一部を担えても、各業務の台帳、計算、訂正、連携は別途必要になる。
- ブラウザはサインイン・登録・デバイス認証が中心。日常の管理を誰でも画面で完結できるかは、APIの機能数と分けて評価する。評価の操作入口はMCP・CLI・API。

## 追加機能の評価基準

- 業務範囲を、受付、事実の記録、判断、確定、訂正、外部連携に分ける。それぞれの正本、判断者、対象期間、版を決める。
- 時刻・残高・資格を誤ると人の権利や給与が変わる機能は高リスクとする。規程の適用開始日、遡及変更、監査、障害時の復旧まで受入条件に含める。
- ロールと会社上の資格、実際に起きた事実と承認結果、原本と集計値を分ける。評価できない操作は拒否し、未処理の事実は調査できるよう残す。
- 新機能の採用前に、通常操作、認可違反、欠落、重複、競合、訂正、再実行を検証する。外部連携は送信成功と相手側の業務反映を区別する。

## 資料の維持

機能の追加や所有変更時は、該当層の一覧と詳細仕様を同時に更新する。法令や規程に依存する機能は、根拠、対象範囲、確認日、例外、再確認の担当を記録する。検討中の設計は調査資料に置き、実装状態が変わった時点で一覧へ反映する。
