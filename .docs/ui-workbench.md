# UI の開発環境

## 意図と所有

部品は `web/src/components/ui` に取り込んだ部品集を使う。振る舞い（キーボード、focus、ARIA、エージェントからの操作）は部品が持ち、見た目は部品のclassと `globals.css` の色のtokenで決まる。製品が所有するのは、画面の組み立てと色の値だけ。取り込んだ部品は手で書き換えず、更新は取り込み直しで行う。

部品集とその土台はベータ版でAPIが変わりうる。更新時は変更点を確認し、Storybookの表示・操作・アクセシビリティ検査を通してから上げる。視覚の規約はルートのDESIGN.mdを使う。

## 確認

Storybookは実APIやDBを起動せず、全ページと共通部品を操作する。Controls、イベント、Docs、アクセシビリティ、viewport、明暗、背景と操作テストを使う。新しいページや部品を追加したらstoryも追加する。

Homeでは管理権限、一般利用者、従業員との未連携、空、失敗と遅延を確認する。認証ページでは方式、無効な設定、入力、エラー、確認コードの承認・拒否を確認する。パスキーのOS操作と外部認証は実環境の検証に残す。

Storybookのモックはstoryごとに独立して初期化する。成功するstoryだけで認可や実DBの正しさを証明しない。[[index]]にある基盤の検査も維持する。

## 検証からの改善

操作とアクセシビリティの検査で、mainの入れ子、表示名と操作名の不一致、薄い文字とエラー文字のコントラスト不足が判明した。独自UIと独自テーマ側で修正し、保存版は比較できるように保持した。

自動の操作・アクセシビリティ検査は、利用者が動きを減らす設定を選んだ状態で実行し、装飾的な遷移の途中を確定状態として誤判定しない。通常のプレビューでは利用者の設定に従って動きを残す。実検証で見つかったlandmarkの入れ子、メニューの名前、文字のコントラストは、参照版ではなく独自UIで修正した。

## 互換性と次の作業

通常ページのURLやAPI契約は変更しない。業務contextにstoryや開発用のデータを持ち込まない。以後の業務画面はページを実装するときに空・pending・失敗のstoryを同時に追加する。
