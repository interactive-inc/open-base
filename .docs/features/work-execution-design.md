# AI業務実行台帳の設計

## 目的

権限を持つ利用者が、どのAIが、いつ、どの業務を実行し、どんな結果になったかを検索できるようにする。業務slugで繰り返し実行を束ね、顧客や案件からも履歴を辿れるようにする。

## 所有境界

- Systemは既存のagent Principal、機械用資格情報、操作権限と監査を所有する。
- 業務contextの `work-execution` は業務定義とその版、実行記録と参照を所有する。
- 顧客、案件、引き継ぎノート、成果物は、所有元が発行するIDで参照する。実行台帳から他の業務contextへ直接依存しない。
- 参照先の詳細は、参照先自身の認可を通じて読む。実行台帳に対象名、顧客情報、プロンプト、資格情報、成果物本文を複製しない。

## 業務の登録

- 業務定義にはUUID、登録後に変更しない一意のslug、表示名、短い説明、利用状態を持たせる。表示名や説明の変更は新しい版にする。
- 業務を登録するときは実行者となるagentを用意し、業務定義にそのPrincipal IDを必須で紐づける。担当agentの変更は業務定義の新しい版にする。
- 初期版は業務専用のagentを使う。一度割り当てたagentは別の業務に割り当てない。運用責任者と外部アプリIDはその業務の定義の版に含める。
- 業務定義には任意のタグを複数付けられる。たとえば「顧客対応」と「定期フォロー」を付け、必要に応じて両方で絞り込む。初期版では親子関係を固定せず、部署や目的をまたぐ業務にも同じタグを使えるようにする。
- タグは業務定義の版に含める。業務一覧は現在のタグ、実行履歴は実行時の版に保存されたタグで絞り込む。
- 業務は追加・廃止できる。廃止時は利用終了の版を追加し、終了日時と理由を残す。過去の定義と実行履歴を保持し、廃止済みのslugは別の業務に再利用しない。
- 業務定義を登録・変更・廃止する権限と、実行結果を記録する権限を分ける。未登録または利用終了済みの業務への新規実行記録は拒否する。
- 業務定義は記録の分類と意味を揃えるために使う。手順、チェックリスト、プロンプトの本文は外部の文書やテキストファイルで管理し、データベースには短い説明と任意の参照先だけを保持する。文書の取得や業務の起動は実行環境が担う。

## 初期版の記録

- 一回の実行にUUIDを割り当て、登録済みの業務定義IDと適用した版を紐づける。一つの業務に複数の実行が紐づく。小文字英数字とハイフンで構成した業務slugは、CLI・MCP・APIから業務を指定するために使う。
- 記録にはagent Principal ID、開始・終了日時、サーバー受領日時、結果の区分、短い結果概要を持つ。結果の区分は成功・失敗・要確認。実行環境の申告時刻とサーバー受領時刻を区別する。
- 顧客・案件などの対象と成果物は、種類とIDの組として複数記録できる。件数と文字数に上限を設ける。
- 実行記録は追記する。通信再試行では同じ実行IDと同じ内容を送る。業務の版や利用状態が変わっていても、認可を再検査したうえで、受付済みの同じ記録を返す。同じagentと実行IDに異なる内容が届いたときは競合として扱う。誤記の訂正は元の実行IDを参照する追記に分ける。

## 認証と開示

- 実行環境は既存の機械用資格情報で短命トークンを取得する。書き込みでは、認証されたagentが適用する業務定義の版に紐づく実行者であることと、記録権限を検査する。記録するagent IDは認証結果から確定する。
- 新規記録は現在有効な版を受け付ける。業務を改訂または廃止した直後に旧版の実行結果が到着した場合は競合として扱う。
- 資格情報の失効と権限変更を、実行記録と監査を書き込む直前に同じトランザクションで再検査する。評価不能時は拒否する。
- 機械認証で確認できるのは報告したagent。成果物の正確さや、AIが申告した実行時刻は独立した検証対象とする。人の依頼者を確認できる連携では、検証済みの依頼者を別に記録する。
- 初期版の閲覧は台帳全体への専用権限を持つ利用者に限定する。対象IDや結果概要も機密情報になり得る。対象別に公開範囲が異なる運用では、配備前に参照先との認可合成を追加する。

## agentの運用責任者

- 業務に使うagentごとに、現在在籍する従業員を運用責任者として一人登録する。異常時の連絡先と引き継ぎ先を明確にするため、担当の変更は有効日時・操作者・理由とともに履歴に残す。
- Systemがagentの身元を管理し、`work-execution` が業務運用上の責任者をCompanyの従業員IDで参照する。責任者の登録や変更は管理権限を持つ人が行う。責任者であることによる資格情報や閲覧権限の付与は、別の認可操作で行う。
- 実行したagent、業務を依頼した人、agentの運用責任者を区別する。責任者の異動や退職時には、履歴を保ったまま後任へ引き継げるようにする。

## 外部アプリとの紐付け

- agentの運用設定に、対応する外部アプリのIDを任意で一つ登録する。配備側の連携設定で、どのagentに対応するアプリか確認するために使う。
- Botは人との接点として任意で設ける。Botがない業務も、実行環境がagentとして認証し、同じ実行台帳に記録する。
- アプリIDは参照用の識別子とする。実行記録の主体は機械用資格情報から確定する。

## 実装の順序

- 業務定義の登録・版管理、agentによる追記、業務slug・agent・日時・対象での検索をAPIに追加する。
- CLIとMCPで業務定義の操作と実行履歴の検索を提供する。実行環境からの追記は機械認証で行い、人のMCPセッションと区別する。
- 受入テストでは、別agentを名乗る要求、人・serviceによる実行記録の書き込み、失効、未登録・利用終了の業務、版の変更後も維持される履歴、同時送信、再送、異なる内容での再利用、参照先の権限不足を検証する。

## 操作入口

- `ENABLED_OPT_IN_APPS` に `work-execution` を指定し、必要な主体に `work_execution:read`、`work_execution:manage`、`work_execution:record` を付与する。
- CLIでは `base work-execution definitions save --data <file>` で定義を保存し、`base work-execution runs list --slug <slug>` で実行履歴を読む。
- MCPでは `work_execution_definitions`、`work_execution_save_definition`、`work_execution_runs` を使う。
- 実行環境は担当agentのトークンで `POST /api/work-execution/runs` を呼ぶ。人の操作に使うCLI・MCPは業務定義と履歴の照会を扱う。
