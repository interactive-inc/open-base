# クライアント開発環境

## 目的と境界

UIの設計・状態確認を実アカウントやDBの準備から切り離す。通常のVoidアプリは維持し、開発用Vite入口、Storybook、試験だけでモックを使う。業務の正本、認可、監査、migrationをモック側へ移さない。[[system]] と [[company]] の責任は変わらない。

## UIの所有

部品の振る舞いと見た目はui-sdkとその既定スタイルに任せ、製品は画面の組み立てだけを所有する。

## モックを使う理由

MSWの同じhandlerをVite、ブラウザーのStorybook、Nodeの試験で使い、画面のためだけに別サーバーを維持しない。初期状態は固定の架空値とし、管理者、通常メンバー、従業員未連携、空、低速、失敗、未認証の違いを再現する。画面がまだ存在しない業務APIを網羅したとは主張しない。

独立した開発入口で探索の起点が変わっても画面のスタイルを欠落させないため、Tailwindの対象を実際のページと製品コンポーネントに明示する。

毎回独立したインメモリ状態を標準とする。複数の要求をまたぐ状態を再起動後にも確認したい場合だけ、OSの一時ディレクトリーにSQLiteのsnapshotを保存する。これは開発用の状態保存であり、D1のSQL・制約・同時実行・本番認可の正しさを証明しない。既存のD1と受入試験は引き続き必要。

パスキーと外部IdPは実機・通常環境で確認する。モックではパスキー操作を成功扱いせず、未対応と表示する。デバイス承認は架空コードで状態遷移を確認できる。モックの認証clientへの差し替えは専用設定だけで行い、本番の認証経路へ例外を追加しない。

## Storybookの役割

各ページと製品コンポーネントを、単独の状態と操作の例として管理する。DocsとControlsで利用方法を確認し、Actionsで操作を記録し、表示幅・背景・テーマで見え方を比べる。アクセシビリティ検査とplay関数は、人が実ブラウザーで操作する確認を補完する。全画面を表示できることと、全ての業務シナリオが検証済みであることを区別する。

## 検証と残る仕事

独立シード、権限別応答、未定義APIの拒否、通知の状態変更、デバイス承認の再送拒否、一時SQLiteの再読込、Node内での通信差し替えを試験する。画面追加時は対応storyと必要なhandlerを同時に追加する。外部認証の実機確認、業務ごとのバックエンド受入と配備は別の工程に残る。

## 開発支援

業務基盤の開発では共通の専門ワークフローを利用し、仕様・所有境界・検証の運用を揃える。導入済みの `inta` をプロジェクト設定で有効にし、スキルを複製せず上流の改善を利用する。端末固有のインストール先や許可設定は共有しない。
